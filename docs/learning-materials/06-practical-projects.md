# 實作任務：熱水瓶智慧化改造

## 專案概述
以日本熱水瓶為實體案例，設計三個由淺入深的實驗任務。每個任務附上虛擬碼與邏輯流程圖，並標註「軟體工程師最容易掉進去的硬體坑」。

---

## 任務一：基礎 GPIO 控制與溫度監控

### 目標
建立基本的硬體介面，能夠模擬按鈕並讀取溫度。

### 硬體需求
- ESP32 開發板
- 繼電器模組（模擬按鈕）
- NTC 熱敏電阻（10kΩ）
- 固定電阻（10kΩ）
- LED 指示燈
- 按鈕（用於測試）

### 功能需求
1. 透過繼電器模擬按下熱水瓶的「煮水」按鈕（持續 100ms）
2. 每秒讀取一次 NTC 溫度並透過序列埠輸出
3. LED 指示當前狀態（閃爍 = 待機，常亮 = 加熱中）
4. 支援透過序列埠命令觸發按鈕模擬

### 偽代碼
```
// 全域變數
定義 GPIO:
    RELAY_PIN = 5
    LED_PIN = 2
    NTC_ADC_CHANNEL = ADC1_CHANNEL_6

狀態變數:
    lastButtonPress = 0
    lastTempRead = 0
    lastLEDBlink = 0
    ledState = false

// 初始化
函式 setup():
    配置 GPIO:
        RELAY_PIN → 輸出模式，初始 LOW
        LED_PIN → 輸出模式，初始 LOW
    
    配置 ADC:
        通道 = NTC_ADC_CHANNEL
        衰減 = 11dB (0~3.3V)
        解析度 = 12-bit
    
    初始化序列埠:
        鮑率 = 115200
    
    輸出啟動訊息

// 主迴圈
函式 loop():
    當前時間 = millis()
    
    // 任務 1：處理序列埠命令
    if (序列埠有資料):
        命令 = 讀取序列埠
        if (命令 == "BOIL"):
            if (當前時間 - lastButtonPress > 500):
                模擬按鈕按壓()
                lastButtonPress = 當前時間
            else:
                輸出 "請求太頻繁"
    
    // 任務 2：讀取溫度（每 1 秒）
    if (當前時間 - lastTempRead >= 1000):
        原始 ADC = 讀取 ADC（8 次平均）
        溫度 = NTC 轉換公式(原始 ADC)
        輸出 "[溫度] ADC=%d, 溫度=%.2f°C", 原始 ADC, 溫度
        lastTempRead = 當前時間
    
    // 任務 3：LED 狀態指示（每 500ms 閃爍）
    if (當前時間 - lastLEDBlink >= 500):
        ledState = !ledState
        寫入 LED_PIN(ledState)
        lastLEDBlink = 當前時間

// 按鈕模擬函式
函式 模擬按鈕按壓():
    輸出 "[動作] 模擬按下煮水按鈕"
    寫入 RELAY_PIN(HIGH)
    非阻塞延遲(100ms)  // 重要：不可用 delay()
    寫入 RELAY_PIN(LOW)
```

### 邏輯流程圖
```
開始
 │
 ├─→ 初始化 GPIO、ADC、序列埠
 │
 └─→ 主迴圈
      │
      ├─→ 檢查序列埠命令
      │    └─→ 收到 "BOIL" 且間隔 >500ms
      │         └─→ 繼電器 ON → 100ms → 繼電器 OFF
      │
      ├─→ 檢查溫度讀取時間
      │    └─→ 距離上次 ≥1000ms
      │         └─→ 讀取 ADC → 轉換溫度 → 輸出
      │
      └─→ 檢查 LED 閃爍時間
           └─→ 距離上次 ≥500ms
                └─→ 切換 LED 狀態
```

### 軟體工程師的硬體坑
1. **阻塞式延遲**
   - ❌ 錯誤：使用 `delay(100)` 來控制按鈕持續時間
   - 💥 後果：整個系統停擺 100ms，無法處理其他任務
   - ✅ 正解：使用狀態機或時間戳實現非阻塞延遲

2. **ADC 雜訊處理**
   - ❌ 錯誤：直接使用單次 ADC 讀值
   - 💥 後果：溫度讀值跳動劇烈（±5°C）
   - ✅ 正解：多次採樣平均（至少 8 次）

3. **按鈕彈跳**
   - ❌ 錯誤：未加防抖動機制
   - 💥 後果：一次按壓被識別為多次
   - ✅ 正解：軟體防抖 + 硬體濾波電容

4. **繼電器驅動不足**
   - ❌ 錯誤：直接用 GPIO 驅動繼電器（電流不足）
   - 💥 後果：繼電器無法可靠吸合，或燒毀 GPIO
   - ✅ 正解：使用電晶體或 MOSFET 隔離驅動

5. **溫度轉換公式錯誤**
   - ❌ 錯誤：Beta 值或固定電阻值不精確
   - 💥 後果：溫度偏差 ±10°C
   - ✅ 正解：實測校正（冰水 0°C、沸水 100°C）

## 任務二：狀態機與自動控制

### 目標
實作完整的煮水與保溫邏輯，使用 FSM 管理系統行為。

### 功能需求
1. 四個狀態：IDLE、HEATING、KEEP_WARM、FAULT
2. 自動煮水至 100°C，然後進入保溫模式（85°C）
3. 保溫時溫度低於 83°C 自動重新加熱
4. 加熱超時保護（15 分鐘）
5. 溫度異常檢測（連續 3 次超過 110°C 進入 FAULT）
6. 透過 WiFi/MQTT 接收遠端命令

### 偽代碼
```
// 狀態定義
列舉 State:
    IDLE = 0
    HEATING = 1
    KEEP_WARM = 2
    FAULT = 3

// 全域變數
當前狀態 = IDLE
狀態進入時間 = 0
當前溫度 = 25.0
目標溫度 = 0
過熱計數 = 0
錯誤旗標 = 0

// 狀態機初始化
函式 FSM_Init():
    當前狀態 = IDLE
    狀態進入時間 = millis()
    輸出 "[FSM] 初始化完成，狀態 = IDLE"

// 狀態轉換
函式 FSM_EnterState(新狀態):
    輸出 "[FSM] %s → %s", 當前狀態名稱, 新狀態名稱
    
    當前狀態 = 新狀態
    狀態進入時間 = millis()
    
    switch (新狀態):
        case IDLE:
            繼電器 = OFF
            目標溫度 = 0
            LED模式 = 閃爍
        
        case HEATING:
            繼電器 = ON
            目標溫度 = 100.0
            LED模式 = 常亮
            輸出 "[動作] 開始加熱"
        
        case KEEP_WARM:
            目標溫度 = 85.0
            LED模式 = 慢閃
            輸出 "[動作] 進入保溫模式"
        
        case FAULT:
            繼電器 = OFF
            LED模式 = 快閃
            輸出 "[錯誤] 系統進入故障狀態，旗標=0x%04X", 錯誤旗標

// 狀態機更新（主迴圈呼叫）
函式 FSM_Update():
    當前溫度 = 讀取溫度並濾波()
    當前時間 = millis()
    狀態持續時間 = 當前時間 - 狀態進入時間
    
    // 全域異常檢測
    if (當前溫度 > 110.0):
        過熱計數++
        if (過熱計數 >= 3):
            錯誤旗標 |= 0x0001  // ERR_OVER_TEMP
            FSM_EnterState(FAULT)
            return
    else:
        過熱計數 = 0
    
    // 各狀態邏輯
    switch (當前狀態):
        case IDLE:
            // 等待外部命令
            if (收到 "START_BOIL" 命令):
                FSM_EnterState(HEATING)
        
        case HEATING:
            // 超時保護
            if (狀態持續時間 > 15 * 60 * 1000):
                錯誤旗標 |= 0x0004  // ERR_TIMEOUT
                FSM_EnterState(FAULT)
                return
            
            // 達到目標溫度
            if (當前溫度 >= 目標溫度):
                FSM_EnterState(KEEP_WARM)
        
        case KEEP_WARM:
            if (當前溫度 < 83.0):
                // 溫度過低，重新加熱
                繼電器 = ON
                輸出 "[動作] 溫度過低，重新加熱"
            else if (當前溫度 >= 85.0):
                // 達到保溫溫度，停止加熱
                繼電器 = OFF
            
            // 支援重新煮沸
            if (收到 "RE_BOIL" 命令):
                FSM_EnterState(HEATING)
        
        case FAULT:
            // 只能透過重置恢復
            if (收到 "RESET" 命令 AND 當前溫度 < 100.0 AND 錯誤已清除):
                錯誤旗標 = 0
                FSM_EnterState(IDLE)

// 主迴圈
函式 loop():
    FSM_Update()
    處理 WiFi/MQTT()
    更新顯示()
    看門狗餵養()
```

### 邏輯流程圖
```
        ┌─────────────┐
        │    IDLE     │ ←─────┐
        │  (繼電器OFF)│       │
        └──────┬──────┘       │
               │ START_BOIL   │ RESET
               ↓              │
        ┌─────────────┐       │
        │   HEATING   │       │
        │  (繼電器ON) │       │
        │  目標:100°C │       │
        └──────┬──────┘       │
               │ 達到100°C    │
               ↓              │
        ┌─────────────┐       │
        │ KEEP_WARM   │       │
        │ (繼電器PWM) │       │
        │  目標:85°C  │       │
        └──────┬──────┘       │
               │              │
               │ 過熱/超時/   │
               │ 感測器異常   │
               ↓              │
        ┌─────────────┐       │
        │    FAULT    │───────┘
        │  (繼電器OFF)│
        └─────────────┘
```

### 軟體工程師的硬體坑
1. **狀態轉換時忘記更新硬體**
   - ❌ 錯誤：狀態變數改了，但繼電器未動作
   - 💥 後果：狀態機顯示 IDLE，但加熱器仍在工作
   - ✅ 正解：在狀態進入函式中同步更新所有硬體

2. **保溫邏輯錯誤**
   - ❌ 錯誤：持續開關繼電器（如每秒判斷一次）
   - 💥 後果：繼電器壽命快速耗損（機械壽命 ~10萬次）
   - ✅ 正解：使用遲滯控制（如 83°C 加熱，85°C 停止）

3. **缺少超時保護**
   - ❌ 錯誤：認為一定能達到目標溫度
   - 💥 後果：如果加熱器故障，系統永遠卡在 HEATING
   - ✅ 正解：每個狀態都設超時限制

4. **邊界條件處理不當**
   - ❌ 錯誤：在 KEEP_WARM 收到 START_BOIL 命令沒有處理
   - 💥 後果：使用者按了按鈕沒反應
   - ✅ 正解：繪製完整的狀態轉換表，涵蓋所有可能

5. **異常恢復條件過於寬鬆**
   - ❌ 錯誤：FAULT 狀態立即允許重置
   - 💥 後果：過熱後立即重啟，持續過熱導致危險
   - ✅ 正解：必須等待溫度降至安全範圍才允許重置

## 任務三：完整的穩定性與通訊系統

### 目標
建立生產級的穩定系統，支援遠端監控、OTA 更新、異常診斷。

### 功能需求
1. **看門狗保護**：5 秒超時，條件式餵養
2. **硬體中斷保護**：緊急停止、傾倒感測器
3. **黑盒子記錄**：記錄最近 32 筆事件
4. **MQTT 通訊**：
   - 訂閱：`kettle/command`（接收命令）
   - 發布：`kettle/status`（每 5 秒上報狀態）
   - 發布：`kettle/alert`（異常警報）
5. **OTA 韌體更新**：支援遠端更新
6. **Web 介面**：提供即時監控與控制

### 偽代碼（核心邏輯）
```
// 全域變數
系統健康狀態 = {
    感測器正常: true,
    WiFi 連線: false,
    FSM 正常: true,
    上次更新: 0
}

黑盒子 = 循環緩衝區[32]

// 初始化
函式 setup():
    // 1. 硬體初始化
    GPIO_初始化()
    ADC_初始化()
    繼電器_初始化()
    
    // 2. 看門狗初始化
    esp_task_wdt_init(5秒, true)  // 5 秒超時，啟用重啟
    esp_task_wdt_add(NULL)
    
    // 3. 中斷初始化
    配置緊急停止中斷(PIN_EMERGENCY, 下降沿)
    配置傾倒感測器中斷(PIN_TILT, 任意邊沿)
    
    // 4. 診斷系統
    讀取重啟原因()
    if (重啟原因 == 看門狗):
        錯誤旗標 |= ERR_WATCHDOG
        輸出 "[警告] 系統從看門狗重啟恢復"
    
    從 NVS 讀取統計數據()
    
    // 5. WiFi 初始化
    WiFi_連線(SSID, PASSWORD)
    等待連線(最長 10 秒)
    
    // 6. MQTT 初始化
    MQTT_連線(BROKER_URL)
    MQTT_訂閱("kettle/command", 命令處理回呼)
    
    // 7. 狀態機初始化
    FSM_Init()
    
    輸出 "[系統] 初始化完成"

// 中斷服務程式
函式 IRAM_ATTR 緊急停止_ISR(參數):
    gpio_set_level(RELAY_PIN, 0)  // 立即斷電
    緊急停止旗標 = true

函式 IRAM_ATTR 傾倒感測器_ISR(參數):
    gpio_set_level(RELAY_PIN, 0)  // 立即斷電
    傾倒旗標 = true

// 看門狗餵養
函式 看門狗_智能餵養():
    當前時間 = millis()
    
    // 檢查系統健康
    感測器正常 = (當前時間 - 上次溫度讀取 < 200ms)
    WiFi正常 = WiFi.isConnected()
    FSM正常 = (錯誤旗標 == 0)
    
    系統健康 = 感測器正常 AND FSM正常  // WiFi 非必須
    
    if (系統健康):
        esp_task_wdt_reset()
    else:
        輸出 "[警告] 系統異常，停止餵狗"
        輸出 "  感測器=%d, WiFi=%d, FSM=%d", 感測器正常, WiFi正常, FSM正常

// 黑盒子記錄
函式 黑盒子_記錄():
    條目 = {
        時間戳: millis(),
        狀態: 當前狀態,
        溫度: 當前溫度,
        錯誤旗標: 錯誤旗標,
        重啟原因: esp_reset_reason()
    }
    
    黑盒子[寫入索引] = 條目
    寫入索引 = (寫入索引 + 1) % 32
    
    // 異常時立即保存到 NVS
    if (錯誤旗標 != 0):
        NVS_保存黑盒子()

// MQTT 狀態發布
函式 MQTT_發布狀態():
    JSON = {
        "state": 狀態名稱[當前狀態],
        "temperature": 當前溫度,
        "target": 目標溫度,
        "uptime": millis() / 1000,
        "rssi": WiFi.RSSI(),
        "errors": 錯誤旗標
    }
    
    MQTT_發布("kettle/status", JSON)

// 命令處理
函式 命令處理回呼(topic, payload):
    命令 = 解析 JSON(payload)
    
    switch (命令["action"]):
        case "start_boil":
            if (當前狀態 == IDLE):
                觸發事件(EVENT_START_BOIL)
        
        case "stop":
            觸發事件(EVENT_EMERGENCY_STOP)
        
        case "reset":
            if (當前狀態 == FAULT):
                觸發事件(EVENT_RESET)
        
        case "get_logs":
            黑盒子_匯出()
            MQTT_發布("kettle/logs", 黑盒子資料)

// 主迴圈
函式 loop():
    當前時間 = millis()
    
    // 任務 1：溫度讀取 (100ms)
    if (當前時間 - 上次溫度讀取 >= 100):
        當前溫度 = 讀取並濾波溫度()
        上次溫度讀取 = 當前時間
    
    // 任務 2：狀態機更新 (50ms)
    if (當前時間 - 上次FSM更新 >= 50):
        FSM_Update()
        上次FSM更新 = 當前時間
    
    // 任務 3：MQTT 處理 (10ms)
    if (當前時間 - 上次MQTT處理 >= 10):
        MQTT_Loop()  // 非阻塞處理
        上次MQTT處理 = 當前時間
    
    // 任務 4：狀態發布 (5000ms)
    if (當前時間 - 上次狀態發布 >= 5000):
        MQTT_發布狀態()
        上次狀態發布 = 當前時間
    
    // 任務 5：看門狗餵養 (1000ms)
    if (當前時間 - 上次餵狗 >= 1000):
        看門狗_智能餵養()
        上次餵狗 = 當前時間
    
    // 任務 6：黑盒子記錄 (5000ms)
    if (當前時間 - 上次記錄 >= 5000):
        黑盒子_記錄()
        上次記錄 = 當前時間
    
    // 處理中斷旗標
    if (緊急停止旗標):
        FSM_EnterState(FAULT)
        錯誤旗標 |= ERR_EMERGENCY_STOP
        MQTT_發布("kettle/alert", "緊急停止觸發")
        緊急停止旗標 = false
    
    if (傾倒旗標):
        FSM_EnterState(FAULT)
        錯誤旗標 |= ERR_TILT
        MQTT_發布("kettle/alert", "傾倒感測器觸發")
        等待直立()
        傾倒旗標 = false
```

### 軟體工程師的硬體坑
1. **WiFi 阻塞主迴圈**
   - ❌ 錯誤：使用阻塞式 WiFi 連線（如 `WiFi.begin()` 一直等待）
   - 💥 後果：WiFi 連線失敗時系統卡死數十秒
   - ✅ 正解：使用非阻塞式連線 + 超時機制

2. **MQTT 重連風暴**
   - ❌ 錯誤：連線失敗後立即重試
   - 💥 後果：快速耗盡 Broker 連線數，被封鎖
   - ✅ 正解：指數退避策略（1s → 2s → 4s → 8s...）

3. **OTA 更新時未斷電**
   - ❌ 錯誤：OTA 更新期間繼電器仍在工作
   - 💥 後果：更新失敗導致加熱器持續工作
   - ✅ 正解：OTA 前強制進入安全狀態

4. **黑盒子資料未持久化**
   - ❌ 錯誤：黑盒子僅存於 RAM
   - 💥 後果：當機重啟後遺失所有診斷資訊
   - ✅ 正解：異常時立即寫入 NVS

5. **看門狗無條件餵養**
   - ❌ 錯誤：每次都餵狗，不檢查系統健康
   - 💥 後果：系統異常時仍能「活著」，失去保護意義
   - ✅ 正解：條件式餵養，只在系統健康時餵狗

## 測試與驗證

### 單元測試
1. **GPIO 測試**：用邏輯分析儀驗證波形

3. **FSM 測試**：遍歷所有狀態轉換路徑
4. **安全測試**：故意觸發異常，驗證保護機制

### 整合測試
1. **穩定性測試**：連續運行 7 天

3. **異常恢復測試**：模擬斷電、當機、感測器故障
4. **EMI 測試**：在電磁干擾環境下驗證穩定性

- 溫度精度：±1°C

- 看門狗反應時間：<5s
- 系統重啟時間：<3s

## 總結
三個任務由淺入深，涵蓋了從基礎 GPIO 控制到完整生產級系統的全部知識點。最重要的心得：

**硬體開發 ≠ 寫程式讓它能跑**
**硬體開發 = 寫程式讓它在最壞情況下也不會出事**

軟體工程師最大的轉變是：從「快速開發」到「穩健設計」，從「功能實現」到「異常處理」，從「相信輸入」到「驗證一切」。
